# 驭智 MVP 需求文档


张京鹏 · 人工智能学院 · 2026年10月9日 · 初稿

## 1. 项目概述

**一句话定位：** 驭智是面向计算机类课程的考核平台。学生先在没有AI的情况下手写规划文档，再在受限AI的辅助下完成实现；平台记录全过程，事后由评分器给出过程性评价。

**核心原则：** 规划权在学生，实现权开放给AI。

**MVP的目标：** 在2026年10月21日作品提交截止前，做出一条可运行、可演示的完整主线：

学生手写规划文档 → 要求AI实现（文档不清晰时AI反问，学生补全，直到足够清晰）→ AI实现代码 → 运行与排查 → 评分报告

## 2. 用户与使用流程

**学生：** 参加考核，在平台内完成一道题。

**教师：** 事后查看轨迹与评分报告（MVP只做只读展示，不做配置和复核操作）。

**单次考核流程：**

1. 学生进入考题页面，阅读题目。
2. 规划阶段（无AI）：学生在空白规划文档窗口自由编写实现思路并手动保存，每次保存都有留档；AI能看到的是保存的最后一个版本。
3. 实现阶段：学生在AI对话窗口要求AI按规划文档实现。文档足够清晰时，AI直接实现；实现中发现文档不清晰，AI提问题反问学生，学生在文档窗口细化并保存，直到足够清晰，AI再继续执行。规划阶段AI不对文档提任何建议。
4. 运行与排查：学生运行代码，遇到问题时由AI协助排查。
5. 学生提交，考核结束，系统生成结构化轨迹。
6. 事后，评分器读取轨迹并输出评分报告，教师在报告页查看。

**界面布局（参考PTA的做题界面）：**

- 左侧：题目描述。
- 右侧：工作区，设三个标签页：AI对话、规划文档、代码。
- 顶部：计时与“结束考核”。
- AI对话标签页在规划文档首次保存前置灰，保存后解锁，不另设阶段切换。

## 3. 必留功能需求

### 3.1 规划文档窗口与版本记录

**作用：** 整套设计的支点。它是AI反问的锚点，是区分“实现错误”与“规划错误”的依据，也是评分的主要证据。

**需求：**

- 规划阶段不开放任何AI功能。
- 窗口是一页空白的可编辑文本，背后是一份md文档，学生写完后手动保存。
- 新建时为空白文档，不预填提纲，不要求固定结构；学生自由编写自己的实现思路，可使用自然语言或伪代码。
- 每次保存生成一个带时间戳的版本，全文写入日志，不另做版本管理界面。
- 界面显示“已保存／未保存”状态。AI只读取最近一次保存的版本。
- 记录文档输入过程中的粘贴事件（仅记录发生次数与长度，作为辅助信号）。

**验收标准：** 能保存文档并生成版本1；之后每次保存都生成新版本，全文写入日志；AI回答时使用的是最近一次保存的版本。

### 3.2 受限AI对话

**作用：** 项目的核心卖点，用上下文工程（Harness）实现“规划权保留、实现权开放”。MVP阶段通过系统提示词实现，明确AI只负责执行，不能代替学生规划，并在执行任务时参考学生的规划文档。具体提示词后续单独设计。

**每次调用提供给AI的内容：**

- 系统提示词（含规则，并要求AI执行任务时参考规划文档）
- 最近一次保存的规划文档
- 代码窗口中的当前代码
- 最近一次运行结果
- 对话历史

**反问规则（实现过程中发现文档不清晰时）：**

- AI以学生保存的最新版文档为依据，只在实现过程中发现文档不清晰时才反问，如边界情况、输入为空时的处理、模块间传递的数据未说明。
- 文档足够清晰时，AI不反问，直接实现。
- 一次只提一个问题，等学生细化并保存文档后再继续，直到文档足够清晰再执行。
- 不提供设计方案、模块划分或技术选型，也不评价或修改规划文档。

**执行阶段的规则：**

- AI可以实现代码、调试、解释报错。
- 排查时，AI先对照最新版文档检查代码是否与文档一致：
  - 不一致，属于实现错误，AI直接定位并修复。
  - 一致但结果不符合预期，说明问题可能在规划，AI指出这一点并交还学生修订文档，不自行改动方案。
- AI的上述判断要在回复中明确写出，供评分器和教师从对话记录中复核。

**验收标准：** 在示例考题上，面对故意留有模糊点的文档，AI在实现时能提出相关问题且不给出设计方案，学生补全后再继续；文档足够清晰时，AI直接实现；对一个故意构造的规划错误，AI能指出问题在文档而不是直接改方案。

**配套测试：** 设计提示词的同时，准备一组“诱导AI给出方案”的话术作为测试用例，用来验证AI不会越权。

### 3.3 结构化轨迹日志

**作用：** 评分器的唯一数据来源。日志格式需要最先确定，后期修改成本很高。

**事件字段：**

- session\_id：一次考核的唯一标识
- timestamp：时间戳
- type：事件类型
- payload：事件内容

**事件类型（MVP）：** session\_start、session\_end（会话起止）；doc\_save（保存规划文档，含全文）；chat\_user、chat\_ai（学生与AI的对话）；code\_apply（AI回复中的代码写入代码窗口）；code\_edit（学生在代码窗口手改，运行时记录快照）；code\_run（运行的代码、输出与退出状态）；paste（粘贴，记录长度与所在标签页）。AI的反问和对错误类型的判断，评分器直接从对话中读取，不单独记事件。

**存储：** 每个session一个JSONL文件，只追加写入，每条记录带唯一的event\_id，供评分器引用证据；MVP不需要数据库服务。

**验收标准：** 一次完整考核结束后，能导出一份包含上述事件、按时间排序、可被评分器直接读取的完整轨迹。

### 3.4 过程评分器

**作用：** 把“过程性考核”落到实处，事后运行，不要求实时性。

**输入：** 一次考核的完整结构化轨迹。

**评分维度（暂定，权重待与指导教师商定）：**

- 规划质量（30分）：拆解是否合理完整、关键接口与边界是否考虑到
- 缺口补全（30分）：AI指出的缺口，学生是否有效补全，补得是否正确
- 指挥与校验（40分）：指挥AI是否清晰，是否自己运行验证，是否发现AI的错误，是否在排查时先提出判断
- 违规尝试（扣分，最多扣15分）：诱导AI替代规划、越狱等行为

**输出：** 考核结束后调用一次模型，输出JSON：每个维度的分数、理由和引用的event\_id；总分；一段简短评语。分数为建议值，最终以教师确认为准。

**证据校验：** 程序检查评分结果引用的event\_id是否都存在于日志中，不存在则重新评分，防止模型编造证据。

**评分细则：** 具体的rubric后续单独撰写。

**验收标准：** 对同一份轨迹，评分结果和证据前后基本一致；证据引用能在日志中找到对应事件。

### 3.6 最简报告页

**作用：** 评委看演示视频时最直观的页面，体现“过程性考核”。

**状态：** 具体需求后续再定，以下为初步设想。

**需求（只读）：**

- 轨迹时间线，按时间展示关键事件。
- 规划文档各版本，并能看到版本间的差异。
- 评分报告：各维度分数、证据引用、总分、评语。

**验收标准：** 打开一次考核的报告页，能完整看到上述三部分内容。

### 3.7 代码运行（最小版）

**作用：** 没有它，“校验”和“排查”无法演示。

**需求：** 对应“代码”标签页：包含代码编辑器、运行按钮和输出区。运行时用带超时的子进程执行，输出和报错显示在输出区，并作为最近一次运行结果提供给AI。AI回复中的代码块带“写入代码窗口”按钮，学生也可以直接手写。MVP只支持一种语言，不做沙箱和多语言。【具体语言待定】

## 4. 后续规划

以下内容不在本期实现：

- **产品增强：** 入口门控、出口检查、排查强度分档配置、教师配置界面、多题库管理、多语言运行环境与更完善的沙箱、教师复核与调分功能。
- **课程试点：** 选择合适的计算机类课程，在真实考核中检验平台。
- **数据飞轮：** 收集学生与受限AI的交互数据，持续优化限制规则和评分标准。
- **后训练：** 数据积累充分后，探索通过后训练将教育原则写入模型权重，形成专用的教育考核大模型。
